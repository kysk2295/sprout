## 실제 앱에서 추가 발견한 문제와 수정

1. **40초 인사 지연:** 첫 게이트웨이는 기존 AI 기능을 Ollama로 넘기기 위해 MLX 모델을 내렸다. 실제 앱의 다른 AI 요청도 이 경로를 타서 재로딩·대기를 발생시켰다. 최종 게이트웨이는 모든 Qwen 요청을 MLX로 처리한다. JSON 응답은 JSON 및 JSON Schema 검사 후 전달한다. 이전 전환 테스트 파일은 실패한 설계의 기록으로 보관한다.
2. **답변이 다른 문장으로 바뀜:** 기존 코드는 미검증 생성 초안을 표시한 뒤 근거 검사 결과로 교체했다. 초안 delta를 화면에 보내지 않고 최종 답변만 표시하도록 수정했다. 도구 처리·대기 표시는 유지한다.
3. **취미 질문을 기록 조회로 해석:** 같은 “너는 취미가 뭐니”가 단독으로는 chat이지만 잘못된 AI 답변이 있는 대화에서는 read로 바뀌었다. 학습된 Jev 분류와 Qwen 답변 문제를 분리해야 한다.
4. **Qwen의 역할 혼동:** 기존 도구용 지시문으로 잘못된 대화를 재현하면 “너는 수달이니까 취미가 뭐야?”라고 사용자를 캐릭터로 취급했다. 일반 대화 서버 지시문 `CHAT_SYSTEM`을 분리하고 AI 캐릭터의 정체성·말투·현재 질문에 답하는 규칙을 명확히 했다.
5. **한정된 보호 규칙:** 캐릭터 자신의 취미·취향·이름·정체성 질문은 기록 조회 대상에서 제외한다. 할 일·메모 조회 및 생성·완료 등의 복합 요청은 이 규칙에서 제외한다. `source:self_reference_guard`로 표시하며 **학습된 모델의 성과로 계산하지 않는다**.

6. **오류 답변의 재주입:** 실제 앱에 쌓인 6턴 오류 대화에서는 프롬프트 수정 뒤에도 관점 혼동이 남았다. 명시적인 캐릭터 소개·취향 질문에서만 모델 입력의 과거 대화를 제외하고 현재 앱 정보와 질문으로 답하도록 했다. 저장된 대화 기록은 보존하며 다른 대화의 이력은 유지한다. 이 역시 좁은 대응이며 일반적인 여러 턴 맥락 처리가 모두 해결됐다는 뜻은 아니다.

## 검증 및 한계

- 기존 API 전체 테스트, 새 분류 API의 인증·입력 제한·턴 사용량·4회 답변 허용·오류 처리·보호 규칙 테스트 통과.
- 공용 assistantAgent/Target/Decision 테스트, 데스크톱 타입 검사·빌드, 설치 앱 코드 서명 검증 통과.
- 운영 API 이미지의 핸들러 + 실제 모델 게이트웨이: chat/read/write 분류 및 답변 확인. 인증/사용량 저장소는 격리한 테스트용이므로 사용자 기록을 쓰지 않았다 (`jev-live-smoke-result.json`).
- JSON·태그·작업 쪼개기 3개 및 뒤이은 Jev 분류: 모두 통과. 모델 두 개가 계속 상주했다 (`jev-all-mlx-smoke-result.json`). 모든 AI 기능의 품질 평가를 의미하지는 않는다.
- 실제 앱의 기존 대화에서 인사와 취미 질문을 실행했다. 최종 취미 질문 답변은 “난 새로운 이야기를 상상하는 게 좋아. 너는?”, 후속 질문에는 우주선·달·토끼 이야기를 답했다. 새 기록 조회 칩 없음. 게이트웨이 처리 합계는 각각 5.353초, 7.682초이며 UI 전체 응답 시간과 구분한다. `app-verification.json` 참조.
- 외부 health 200, 인증 없는 `/ai/status` 401. Postgres·PowerSync·백업·Uniport 컨테이너 유지.
- 메모리 압력 4 이상 또는 서비스 시작 대비 swap 2GiB 초과 증가 시 새 모델 프로세스를 종료하고 fault를 유지한다. 운영 관측은 단기간이며 장기 안정성을 보장하지 않는다.
- `graphify update .`는 설치된 실행기의 Python 3.12 경로가 없어 실행 실패했다. `sprout-graphify-final.log` 참조.
